# Exponential backoff for status polling

## Problem

The CLI status polling loops (`flux reconcile`, `flux create --wait`,
`flux resume`, `flux bootstrap` health checks) used
`wait.PollUntilContextTimeout` with a fixed two second interval. When the
Kubernetes API kept failing or started rate limiting requests, the CLI kept
issuing a request every two seconds for the whole operation timeout. That
amplified the API server load, turned transient 429 responses into sustained
rate limiting, and left resources stuck in an intermediate state with no
mechanism to space out or recover the polling.

## Design

`internal/retrier` provides a `Poller` with the same condition contract as
`wait.PollUntilContextTimeout`. Each condition evaluation is classified:

| Outcome | Trigger | Scheduling |
| --- | --- | --- |
| `success` | condition returns `(true, nil)` | stop |
| `in_progress` | condition returns `(false, nil)` | fixed initial interval |
| `rate_limited` | HTTP 429, honoring `Retry-After` when present | server hint, capped |
| `transient_error` | 5xx, server/client timeout, network timeout, context deadline | exponential backoff |
| `terminal_error` | any other error, e.g. `NotFound`, readiness failure | returned immediately |

Backoff schedule: `initial * factor^failures`, capped at `max interval`.
Any `success` or `in_progress` evaluation resets the consecutive failure
counter, so when the API recovers the wait collapses back to the initial
interval and a resource left in an intermediate state converges as soon as
possible (self-healing) instead of remaining trapped in a long backoff.

Rate limit handling uses `apierrors.IsTooManyRequests`. When the response
carries `Retry-After`, that duration is honored and capped by
`--retry-max-rate-limit-wait`; otherwise the exponential backoff applies.
Client-side rate limiter waits surface as timeout errors and are retried as
transient errors.

Terminal error handling is unchanged: errors that previously aborted the poll
still abort it on the first occurrence, and the operation timeout still
returns `context.DeadlineExceeded`.

## Configurable parameters

Cluster rate limit thresholds differ, so every backoff parameter is a global
flag. The defaults reproduce the historical cadence while resources are
reconciling without errors.

| Flag | Default | Meaning |
| --- | --- | --- |
| `--retry-initial-interval` | `2s` | base interval; also the fixed in-progress cadence |
| `--retry-max-interval` | `60s` | cap on the exponential backoff |
| `--retry-factor` | `2.0` | growth multiplier per consecutive failure |
| `--retry-jitter-factor` | `0.5` | randomization fraction in `[0,1]`, `0` disables |
| `--retry-max-rate-limit-wait` | `5m` | cap on a single `Retry-After` wait |

Invalid combinations are rejected in the root command `PersistentPreRunE`
with an actionable error (for example max interval below the initial
interval, factor below one, jitter outside `[0,1]`).

## Compatibility

- No existing flag, output format, condition function or readiness semantics
  changed. In-progress polling keeps the same two second cadence.
- The new flags are additive and default to the previous behaviour apart from
  the failure path they are meant to fix.
- `pkg/bootstrap` public method signatures are unchanged; the timeout is still
  applied per health check.

## Evidence

`artifacts/retrier/` contains reproducible evidence generated by
`go run -tags retrier_report ./cmd/retrier-report`, which replays the
schedules on a deterministic virtual clock (jitter disabled):

- `*.trace.json`: per-request elapsed time, outcome and scheduled wait.
- `report.md`: request-count curve per 30 second window with the old fixed
  two second polling baseline.

Headline numbers from the default configuration over a five minute window:

- Sustained failure: requests decay from 4 in the first 30 seconds to at most
  1 per later window; the old fixed polling made 15 requests in every window.
- Rate limiting with a 45 second `Retry-After`: 7 requests in five minutes,
  all spaced by the server-advertised wait.
- Recovery: after four failures the first healthy response resets the
  backoff and the resource converges in 36 seconds.

The same assertions are encoded as unit tests in
`internal/retrier/backoff_test.go` (`//go:build unit`).
